## WHAT WE'RE BUILDING (one paragraph, to be decomposed in the brainstorm)

A **fundamentals + news + sentiment engine**: three coupled capabilities that together let trading-tools reason about *what a company is* and *what's changing about it*, not just its price path. **(A) Fundamentals backbone** — point-in-time financial-statement data (revenue, EPS, margins, growth rates, balance-sheet ratios, etc.) per ticker, keyed by filing date so the backtester never sees a number before it was public; **SEC EDGAR `companyfacts` API** is the planned source (free, genuinely point-in-time via filing dates, ~15-20y depth — needs an XBRL tag→metric mapping, est. ~4-6h; FMP premium $15-30/mo is the fallback if XBRL parsing gets ugly). **(B) Earnings + PEAD** — earnings actual-vs-consensus / surprise / announcement dates (drives post-earnings-announcement-drift and earnings-surprise strategies); **Finnhub free tier** for earnings; Finnhub also has a free news endpoint worth a look. **(C) News + sentiment overlay** — a news feed + a sentiment classifier (LLM via the Claude API, or a vendor sentiment score) → a per-ticker per-day sentiment signal; positive-news → long quality stocks, negative-news → short quality stocks (mixed academic edge, higher complexity — and the *news feed is the one place where "free" is genuinely limited*: Polygon / Benzinga / NewsAPI all cost money, NewsAPI's free tier is tiny, Finnhub free has *some* news — **this is a real cost decision the brainstorm must make**). The integration layer (parked, may be in-scope or a sibling sub-project): **the screener/scanner** — a screen over a candidate pool (Nasdaq-100 / Russell 2000 / S&P 1500; Scott likes the StockTwits Top-25 Momentum lists, screenshots in `d:\TWS API\stockTwits\`) blending momentum/attention (volume coming in, relative-volume, return rank — buildable now from `equity_bars`) + a quality filter (from A) + a news layer (from C); a *live watchlist* tool (`tt scan`) and/or a *universe generator* feeding the backtester (then needs strict point-in-time discipline). Outputs feed back into the existing harness — new cross-sectional strategy family (PEAD, quality, value-momentum, sentiment) measured the same way everything else is (cost-aware, full/IS/OOS, PSR/DSR, vs SPY-BH + asset-BH).

## THE BRAINSTORM — what it needs to settle

The design is **not** approved; this is a real brainstorm. Decisions the brainstorm must produce (the standing rules below are fixed; everything here is open):

1. **Decomposition into shippable sub-pieces and their order.** Strawman: **V3.3a** = fundamentals backbone (SEC EDGAR companyfacts ingester + `fundamentals` table + the XBRL tag→metric mapping + a few derived metrics) — *no strategies yet, just the data layer + a smoke test that it's point-in-time*; **V3.3b** = earnings/PEAD (Finnhub earnings ingester + `earnings` table + a PEAD / earnings-surprise cross-sectional strategy family + baseline); **V3.3c** = news + sentiment (the news feed decision + ingester + `news` table + sentiment classifier + a sentiment-overlay strategy + baseline); **V3.3d** = the screener/scanner (`tt scan` + optionally a point-in-time universe generator). Confirm/revise this; each gets its own spec → plan → ship.
2. **The look-ahead / point-in-time architecture.** This is THE central design problem. SEC EDGAR companyfacts gives you the *filing date* (and the *period* the data covers) — the harness must only use a fundamental fact on bar `t` if it was *filed* on or before `t` (typically with a small reporting-lag cushion; decide). What's the table shape — one row per (symbol, metric, period_end, filed_date, value)? How does a strategy *query* "the latest fact for symbol X as of bar t"? (A `point_in_time_view(symbol, as_of) -> dict[metric, value]` helper, probably.) Restated values (10-K/A amendments) — keep all, query the latest *filed-before-t* one. Pin this with tests that would fail if a future value leaked.
3. **The universe problem.** `TOP_25` is hardcoded, survivorship-biased, ~20 mega-cap tech names. A fundamentals/screener engine either (a) accepts that and stays on `TOP_25` for now (cheapest, but the screener-as-universe-generator idea is then deferred), or (b) takes a step toward a *mechanical point-in-time screen* (scan a broad pool as-of date `T` using only data ≤ `T`; let delisted/fallen names hurt you) — which is the genuinely-survivorship-corrected version, but a much bigger build that needs ingesting hundreds of tickers + delisting data. Decide the near-term scope; this also bears on V3.2b (decorrelated universe — overlapping problem).
4. **The news feed + sentiment classifier.** Free-data-first is the project's standing bias (SEC EDGAR free, Finnhub free, IB for bars), but news is where "free" runs out. Options to weigh: Finnhub free-tier news (limited but free — start here?); Polygon news endpoint (needs a paid tier ~$30+/mo); Benzinga/NewsAPI (paid); deferring news entirely and shipping A+B first. And the classifier: LLM (call the Claude API to score headlines — costs API tokens, fully under our control, no extra vendor) vs a vendor sentiment score (Finnhub/Polygon ship one on some tiers). Decide, and whether news is in the first cut at all.
5. **Where the new strategies plug into the harness.** Cross-sectional strategies (rank all 25 names by a fundamental/sentiment metric, hold the top K, rebalance) don't fit `_walk_signals` (per-instrument). They probably need the V3.2 portfolio-overlay walk (`backtest/portfolio.py`) or a new cross-sectional walk. Decide whether to extend the overlay or add a third walk path. (Note the overlay can't carry fractional positions — relevant if a cross-sectional strategy wants `tiered_meanrev`-style sizing.)
6. **What "derived metrics" the fundamentals layer computes** (so strategies don't each re-derive): TTM revenue/EPS, QoQ and YoY growth, gross/operating/net margin, ROE/ROA, debt/equity, FCF yield, P/E and P/B (needs price too), earnings-surprise %, etc. Keep the raw XBRL facts *and* a derived-metrics layer.

## STANDING RULES (don't re-litigate)

- **Point-in-time discipline is non-negotiable** for anything fundamentals/news/screener: only data that was public *before* the bar being traded. Survivorship bias on `TOP_25` is acknowledged-and-flagged (existing policy) — don't pretend it's solved; if the engine introduces a new universe, that universe is point-in-time-constructed or the survivorship caveat carries forward and is stated in output.
- **Free data first** — SEC EDGAR (free), Finnhub free tier, IB for bars are the established sources; a paid feed (FMP, Polygon, Benzinga) is a deliberate decision with a justification, not a default.
- **Everything is measured the same way:** cost-aware by default in runners (5 bps round-trip); full / IS (first 70% of bars) / OOS (last 30%) split; PSR(0.9) + DSR (multiple-testing-corrected); REAL EDGE = OOS Sharpe > 0.9 ∧ DSR ≥ 0.95; **vs SPY-BH AND vs asset-BH always** (the harness already does this); fit any tunable params *only* on the IS window, the tunables become the DSR trial family; 20-year data window is enough.
- **`binary` stays the default `position_management`**; existing strategies/benchmarks bit-for-bit unchanged by any harness change (confirm with the existing suite).
- **Process:** brainstorming (this is genuinely open) → spec → sign-off → writing-plans → plan approval → TDD implement with frequent commits → final verification + `git push` (branch `master`). One sub-piece at a time; the V3.1 / V3.2 / tiered-port plans in `docs/plans/` are the granularity template (full code in every step, exact commands, expected output, Task 0 green baseline, commit per task).
- **Schema is append-only + idempotent** (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN IF NOT EXISTS`); `db.init_schema()` applies it; `conftest.py`'s TRUNCATE list gains any new table; apply once to `trading_data` after the schema change.
